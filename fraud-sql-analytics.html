01
3D Secure Impact

3DS neutralises 7 typologies out of 8

92% of card fraud bypassed 3DS. The only pattern immune by design: friendly fraud — the victim authenticates the transaction they will later dispute.

card_testing (no 3DS)137 cases · avg €80
velocity (no 3DS)83 cases · avg €470
friendly_fraud (3DS on)19 cases · avg €375
Techniques: triple JOIN · GROUP BY multi-dim · ROUND · AVG
analysis_01_3ds.sql 
SELECT
    ROUND(AVG(fr.amount_disputed), 0) AS avg_loss,
    t.is_3ds_authenticated,
    c.card_tier,
    fr.investigator_notes      AS pattern,
    COUNT(*)                   AS n_cas
FROM fraud_reports fr
JOIN transactions t ON t.transaction_id = fr.transaction_id
JOIN cards c        ON c.card_id        = t.card_id
GROUP BY
    fr.investigator_notes,
    c.card_tier,
    t.is_3ds_authenticated
ORDER BY n_cas DESC;
02
Volume vs Cost

The Volume / Cost Paradox

Card testing floods the queue (37% of cases) while generating almost no financial loss. Wire fraud does the opposite: 31% of cases, 97% of the money. Three distinct economic worlds, three distinct defences needed.

Techniques: window function SUM(COUNT(*)) OVER() · GROUP BY multi-dim · LEFT JOIN
analysis_02_regimes.sql 
SELECT
    fr.fraud_type,
    COUNT(*)                                     AS n_cas,
    ROUND(
      100.0 * COUNT(*) / SUM(COUNT(*)) OVER (),
    1)                                           AS pct_volume,
    c.card_tier,
    ROUND(AVG(fr.amount_disputed), 0)            AS avg_loss
FROM fraud_reports fr
JOIN transactions t  ON fr.transaction_id = t.transaction_id
LEFT JOIN cards c    ON t.card_id = c.card_id
WHERE fr.status = 'confirmed'
GROUP BY fr.fraud_type, c.card_tier
ORDER BY avg_loss DESC;
03
Card Tier

Card fraud is opportunistic, not targeted

Fraud distribution across card tiers mirrors the natural population split almost exactly. Fraudsters draw at random — which means tier-based rules are the wrong defence. Behavioural signals (velocity, geography) are the right ones.

Techniques: COALESCE · LEFT JOIN · comparison with reference dataset
analysis_03_card_tier.sql 
SELECT
    COALESCE(c.card_tier, 'wire') AS tier,
    COUNT(*)                      AS n_cas,
    ROUND(AVG(fr.amount_disputed), 0) AS avg_loss
FROM fraud_reports fr
JOIN transactions tr ON tr.transaction_id = fr.transaction_id
LEFT JOIN cards c    ON c.card_id = tr.card_id
WHERE fr.status = 'confirmed'
GROUP BY c.card_tier;

Techniques: LEFT JOIN with NULL handling · COALESCE · multi-aggregation
analysis_04_merchants.sql 
SELECT
    COALESCE(m.subcategory, 'wire/transfer') AS subcategory,
    COUNT(*)                                 AS n_cas,
    ROUND(SUM(fr.amount_disputed), 0)        AS total_lost_eur,
    ROUND(AVG(fr.amount_disputed), 0)        AS avg_loss
FROM fraud_reports fr
JOIN transactions t   ON fr.transaction_id = t.transaction_id
LEFT JOIN merchants m ON t.merchant_id = m.merchant_id
WHERE fr.status = 'confirmed'
GROUP BY m.subcategory
ORDER BY n_cas DESC
LIMIT 10;
05
Account Takeover

The change precedes the fraud

A significant share of wire frauds (ATO, sim_swap, mule) is preceded by an email/phone/password change in the 24h window — a powerful early-warning signal that pure transaction monitoring misses.

Techniques: CTE · COUNT FILTER (WHERE EXISTS) · INTERVAL · correlated subquery · NULLIF
analysis_05_ato_signal.sql 
WITH fraud_tx AS (
    SELECT
        fr.fraud_id, fr.customer_id, fr.fraud_type,
        fr.amount_disputed,
        t.transaction_timestamp AS fraud_time
    FROM fraud_reports fr
    JOIN transactions t ON t.transaction_id = fr.transaction_id
    WHERE fr.status = 'confirmed'
      AND fr.fraud_type IN ('account_takeover','sim_swap','mule')
)
SELECT
    ft.fraud_type,
    COUNT(DISTINCT ft.fraud_id) AS total_fraud,
    COUNT(DISTINCT ft.fraud_id) FILTER (WHERE EXISTS (
        SELECT 1 FROM customer_changes cc
        WHERE cc.customer_id = ft.customer_id
          AND cc.field_name IN ('email','phone','password')
          AND cc.changed_at
              BETWEEN ft.fraud_time - INTERVAL '24 hours'
                  AND ft.fraud_time
    ))                          AS preceded_by_change
FROM fraud_tx ft
GROUP BY ft.fraud_type
ORDER BY preceded_by_change DESC;
06
Risk Scoring

Multi-signal risk score — no ML needed

5 independent signals (no 3DS, anonymous IP, foreign country, >500km from home, amount anomaly) combined into a 0–5 score that classifies transactions from safe to critical without any machine learning.

score ≥ 4 → CRITICAL tx #700191870 · €1,971
score = 3 → HIGH multiple tx flagged
Techniques: stacked CTEs · AVG() OVER (PARTITION BY) · arithmetic scoring · CASE WHEN classification
analysis_06_risk_score.sql 
WITH scored AS (
    SELECT
        tr.transaction_id, tr.customer_id,
        tr.amount_eur, tr.transaction_timestamp,
        CASE WHEN NOT tr.is_3ds_authenticated         THEN 1 ELSE 0 END AS flag_no_3ds,
        CASE WHEN ls.is_vpn OR ls.is_tor              THEN 1 ELSE 0 END AS flag_anon_ip,
        CASE WHEN tr.ip_country <> c.country          THEN 1 ELSE 0 END AS flag_foreign,
        CASE WHEN tr.distance_from_home_km > 500      THEN 1 ELSE 0 END AS flag_far,
        CASE WHEN tr.amount_eur > 3 * AVG(tr.amount_eur)
                    OVER (PARTITION BY tr.customer_id) THEN 1 ELSE 0 END AS flag_amount
    FROM transactions tr
    JOIN customers c ON c.customer_id = tr.customer_id
    LEFT JOIN login_sessions ls ON ls.session_id = tr.session_id
),
risked AS (
    SELECT *,
        (flag_no_3ds + flag_anon_ip + flag_foreign
         + flag_far + flag_amount) AS risk_score
    FROM scored
)
SELECT transaction_id, amount_eur, risk_score,
    CASE
        WHEN risk_score >= 4 THEN 'critical'
        WHEN risk_score  = 3 THEN 'high'
        WHEN risk_score  = 2 THEN 'medium'
        ELSE                      'low'
    END AS risk_level
FROM risked WHERE risk_score >= 2
ORDER BY risk_score DESC, amount_eur DESC;

Methodology & Honest Limitations

The notebook captures the full exploration trail: 4 phases of EDA, the hypotheses tested, the dead-ends, and — critical for honesty — the biases discovered in the synthetic dataset.

Phase 1

Volumetry

Card tier and account type distributions establish the population baseline before any fraud overlay.

Phase 2

Descriptive

Transaction subtypes, root causes, detection methods, average baskets — what does normal look like?

Phase 3

Investigations

Crossed dimensions: 3DS × tier × fraud type, merchant subcategory loss, reporting delays, victim profile.

Phase 4

Advanced

Window functions, CTEs, geographic impossibility (LAG), weighted risk score, top-N per partition.

Known dataset biases

What the data cannot tell us

  • ▸root_cause drawn uniformly at random — uncorrelated with fraud type. Any variance is noise.
  • ▸mobile_country_code not aligned with nationality — useless as an anti-fraud signal.
  • ▸detection_method generated independently — flatness in distribution is artificial.
  • ▸No card-present fraud modelled (no skimming or physical theft) — 100% of fraud is CNP.
  • ▸Retail-banking skew: 70% checking accounts — premium tiers under-represented in the population.

SQL Skills Demonstrated

Joins

INNER JOIN, LEFT JOIN (with deliberate NULL interpretation), triple JOIN across 3 tables, self-join for sequential analysis.

Window Functions

SUM(COUNT(*)) OVER(), AVG() OVER (PARTITION BY), LAG(), ROW_NUMBER().

CTEs

Simple CTEs and stacked multi-layer pipelines (scored → risked → classified) for readable, testable SQL.

NULL Handling

COALESCE, NULLIF, IS DISTINCT FROM — and understanding why LEFT JOIN is needed when FK columns can be NULL.

Date Arithmetic

INTERVAL, BETWEEN for time windows, EXTRACT(EPOCH FROM ...), AGE(), DATE_TRUNC() for period grouping.

Correlated Subqueries

EXISTS() pattern with temporal correlation — "for each fraud, did a credential change happen in the prior 24h?"
