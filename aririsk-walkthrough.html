01 · Data Profiling Step 1

Data Profiling · Cadrer avant d'analyser

The analyst reflex: check volumes, time bounds, coverage and quality before touching a model. The constraints shape everything — a single tax-arrears snapshot, not a time series. Knowing your data's limits from the start is what separates an analysis from an opinion.

-- ========================================================================= -- 01 — DATA PROFILE : cadrer le périmètre avant d'analyser -- Réflexe "data profiler" : volumes, bornes, qualité, couverture. -- ========================================================================= -- 1.1 --- Vue d'ensemble : volumes + bornes temporelles --------------------- SELECT (SELECT COUNT(*) FROM raw.companies) AS nb_entreprises, (SELECT COUNT(*) FROM raw.annual_reports) AS nb_rapports, (SELECT COUNT(DISTINCT reg_code) FROM raw.annual_reports) AS cos_avec_rapports, (SELECT COUNT(*) FROM marts.distress_label WHERE en_detresse) AS nb_en_detresse, (SELECT COUNT(*) FROM marts.distress_label WHERE en_faillite) AS nb_faillites, (SELECT MIN(report_year) FROM raw.annual_reports) AS annee_min, (SELECT MAX(report_year) FROM raw.annual_reports) AS annee_max, (SELECT COUNT(DISTINCT snapshot_date) FROM raw.tax_arrears) AS nb_snapshots_dettes; -- Résultat (constaté) : 375 886 entreprises, 7 ans de rapports (2019-2025), -- 1 seul snapshot d'arriérés fiscaux (2026-08-10). -- 1.2 --- Répartition par forme juridique + statut -------------------------- SELECT legal_form, status_text, COUNT(*) AS nb FROM raw.companies GROUP BY legal_form, status_text ORDER BY nb DESC LIMIT 20; -- 1.3 --- Répartition sectorielle (EMTAK section), année la plus récente ---- SELECT emtak_section, COUNT(DISTINCT reg_code) AS nb_entreprises FROM marts.ratios WHERE report_year = (SELECT MAX(report_year) FROM marts.ratios) GROUP BY emtak_section ORDER BY nb_entreprises DESC; -- 1.4 --- Couverture "rapports par entreprise" (qui a combien d'années) ----- SELECT nb_reports, COUNT(*) AS nb_entreprises FROM ( SELECT reg_code, COUNT(*) AS nb_reports FROM raw.annual_reports GROUP BY reg_code ) t GROUP BY nb_reports ORDER BY nb_reports; -- 1.5 --- Répartition des années de rapports (densité temporelle) ----------- SELECT report_year, COUNT(DISTINCT reg_code) AS nb_entreprises, COUNT(*) AS nb_rapports FROM raw.annual_reports GROUP BY report_year ORDER BY report_year;
02 · Financial Ratios Step 2

Financial Ratios · Rebuild, then benchmark

The heart of the credit job: reconstruct the ratios by hand from the balance sheet (with NULLIF guards against divide-by-zero), then position a company against its sector's P10 / P50 / P90. A liquidity ratio under the sector's 10th percentile is a real signal, not a number.

Margin / ROA / solvencyYoY growth via LAGSector benchmark P10/P50/P90
-- ========================================================================= -- 02 — FINANCIAL RATIOS : reconstruire les ratios en SQL + positionnement -- Cœur du métier : savoir d'où viennent les ratios, puis situer une entreprise -- face à son secteur (benchmark P10/P50/P90). -- ========================================================================= -- 2.1 --- Reconstruire les ratios à la main depuis le bilan (guards NULLIF) - SELECT reg_code, report_year, revenue, ROUND(100.0 * net_profit / NULLIF(revenue,0), 2) AS marge_nette_pct, ROUND(100.0 * operating_profit / NULLIF(revenue,0), 2) AS marge_op_pct, ROUND(100.0 * net_profit / NULLIF(assets,0), 2) AS roa_pct, ROUND(100.0 * equity / NULLIF(assets,0), 2) AS solvabilite_pct, ROUND(current_assets / NULLIF(current_liabilities,0), 2) AS current_ratio, ROUND(100.0 * (current_liabilities + non_current_liabilities) / NULLIF(assets,0), 2) AS levier_pct FROM raw.annual_reports WHERE NOT COALESCE(consolidated, false) -- on exclut les comptes consolidés AND assets > 0 AND report_year = 2024 ORDER BY reg_code LIMIT 30; -- 2.2 --- Croissance du CA année-sur-année (LAG = fenêtre temporelle) ------- -- LAG() récupère la valeur de la ligne précédente dans la partition (ici par -- entreprise, triée par année) : c'est la brique de base de toute feature "évolution". WITH r AS ( SELECT reg_code, report_year, revenue, LAG(revenue) OVER (PARTITION BY reg_code ORDER BY report_year) AS rev_prev FROM raw.annual_reports WHERE NOT COALESCE(consolidated, false) AND revenue > 0 ) SELECT reg_code, report_year, revenue, rev_prev, ROUND(100.0 * (revenue - rev_prev) / NULLIF(rev_prev,0), 1) AS croissance_pct FROM r WHERE rev_prev IS NOT NULL ORDER BY reg_code, report_year; -- 2.3 --- Positionnement d'une entreprise vs son secteur (benchmark) ------- -- On compare les ratios de l'entreprise aux percentiles P10/P50/P90 du secteur -- et de l'année. Repère : une liquidité SOUS le P10 = signal de risque. SELECT r.reg_code, r.report_year, r.emtak_section, r.liquidite AS ma_liquidite, b.liquidite_p10, b.liquidite_p50, b.liquidite_p90, CASE WHEN r.liquidite < b.liquidite_p10 THEN 'SOUS P10 (risque eleve)' WHEN r.liquidite < b.liquidite_p50 THEN 'sous mediane' ELSE 'au-dessus de la mediane' END AS position_liquidite, r.solvabilite, b.solvabilite_p50, r.roa, b.roa_p50 FROM marts.ratios r JOIN marts.benchmarks_emtak b ON b.emtak_section = r.emtak_section AND b.report_year = r.report_year WHERE r.reg_code = 10051907; -- TODO : remplacer par un vrai reg_code estonien
03 · Cohort Risk Step 3

Cohort & Vintage · Risk across time & segments

The credit-risk reflex: read risk in the time dimension (creation-year cohort) and across segments (sector, size, legal form). Opens with the caveat to name out loud — older cohorts have had more years to become distressed, so their rate is mechanically higher. That vintage effect is exactly what you must mention.

Distress rate by cohortRisk by EMTAK sectorTax-debt → distress bridge
-- ========================================================================= -- 03 — COHORT / VINTAGE : taux de "défaut" par cohorte et segment -- LE réflexe credit risk : regarder le risque dans la dimension du temps -- (cohorte de création) et des segments (secteur, taille, forme juridique). -- ========================================================================= -- 3.1 --- Taux de détresse par cohorte (année de création) ---------------- -- ⚠️ Caveat à EXPLIQUER : les cohortes anciennes ont eu plus d'années pour -- devenir en détresse → plus d'exposition (et donc un taux mécaniquement plus -- élevé). C'est l'effet "vintage" : il faut le mentionner. SELECT EXTRACT(YEAR FROM c.first_registration_date)::int AS annee_cohorte, COUNT(*) AS nb_entreprises, COUNT(*) FILTER (WHERE d.en_detresse) AS nb_detresse, ROUND(100.0 * COUNT(*) FILTER (WHERE d.en_detresse) / NULLIF(COUNT(*),0), 2) AS taux_detresse_pct FROM raw.companies c JOIN marts.distress_label d ON d.reg_code = c.reg_code WHERE c.first_registration_date IS NOT NULL GROUP BY annee_cohorte ORDER BY annee_cohorte; -- 3.2 --- Risque par secteur (EMTAK) — qui est risqué ? --------------------- SELECT r.emtak_section, COUNT(DISTINCT r.reg_code) AS nb, COUNT(DISTINCT r.reg_code) FILTER (WHERE d.en_detresse) AS nb_detresse, ROUND(100.0 * COUNT(DISTINCT r.reg_code) FILTER (WHERE d.en_detresse) / NULLIF(COUNT(DISTINCT r.reg_code),0), 2) AS taux_detresse_pct FROM marts.ratios r JOIN marts.distress_label d ON d.reg_code = r.reg_code WHERE r.report_year = (SELECT MAX(report_year) FROM marts.ratios) GROUP BY r.emtak_section HAVING COUNT(DISTINCT r.reg_code) > 50 -- on ignore les petits échantillons ORDER BY taux_detresse_pct DESC; -- 3.3 --- Risque par forme juridique -------------------------------------- SELECT d.legal_form, COUNT(*) AS nb, COUNT(*) FILTER (WHERE d.en_detresse) AS nb_detresse, ROUND(100.0 * COUNT(*) FILTER (WHERE d.en_detresse) / NULLIF(COUNT(*),0), 2) AS taux_pct FROM marts.distress_label d GROUP BY d.legal_form HAVING COUNT(*) > 20 ORDER BY taux_pct DESC; -- 3.4 --- Risque par taille (bandes de chiffre d'affaires, dernière année) -- SELECT CASE WHEN r.revenue IS NULL THEN 'inconnu' WHEN r.revenue < 100000 THEN 'micro (<100k)' WHEN r.revenue < 2000000 THEN 'petite (100k-2M)' WHEN r.revenue < 10000000 THEN 'moyenne (2M-10M)' ELSE 'grande (>10M)' END AS bande_taille, COUNT(DISTINCT r.reg_code) AS nb, COUNT(DISTINCT r.reg_code) FILTER (WHERE d.en_detresse) AS nb_detresse, ROUND(100.0 * COUNT(DISTINCT r.reg_code) FILTER (WHERE d.en_detresse) / NULLIF(COUNT(DISTINCT r.reg_code),0), 2) AS taux_pct FROM marts.ratios r JOIN marts.distress_label d ON d.reg_code = r.reg_code WHERE r.report_year = (SELECT MAX(report_year) FROM marts.ratios) GROUP BY bande_taille ORDER BY taux_pct DESC; -- 3.5 --- Le "pont" dette fiscale -> détresse ------------------------------ -- Montre l'information apportée par les arriérés MTA : à quelle fréquence -- une entreprise avec dette fiscale est-elle en détresse ? SELECT a_dette_fiscale, COUNT(*) AS nb, COUNT(*) FILTER (WHERE en_detresse) AS nb_detresse, ROUND(100.0 * COUNT(*) FILTER (WHERE en_detresse) / NULLIF(COUNT(*),0), 2) AS taux_detresse_pct FROM marts.distress_label GROUP BY a_dette_fiscale; -- 3.6 --- Âge des entreprises en détresse (distribution) ------------------- SELECT EXTRACT(YEAR FROM AGE(CURRENT_DATE, first_registration_date))::int AS age_ans, COUNT(*) AS nb_detresse FROM marts.distress_label WHERE en_detresse GROUP BY age_ans ORDER BY age_ans;
04 · PD Features Step 4

Feature Engineering · Build the training table

Assemble ratios + LAG evolution + sector benchmark + target into the table a PD model is trained on. The leading-indicator columns — margin falling, liquidity falling, leverage rising, liquidity under benchmark — capture deterioration, which is what predicts default. Plus a run-length pattern for consecutive loss years.

Panel company × yearLagged ratios (evolution)Consecutive-loss runs
-- ========================================================================= -- 04 — PD FEATURE ENGINEERING : construire la table d'entraînement -- On assemble (ratios + évolutions LAG + benchmark secteur + cible) pour -- ensuite brancher un modèle de probabilité de défaut (PD) en Python. -- ========================================================================= -- 4.1 --- Panel entreprise x année : ratios + LAG + benchmark -------------- WITH feat AS ( SELECT r.reg_code, r.report_year, r.emtak_section, r.revenue, r.marge_nette, r.marge_op, r.roa, r.solvabilite, r.liquidite, r.dette_sur_actif, r.croissance_ca, -- proxy gouvernance : délai de dépôt (jours entre clôture et dépôt) (r.filing_date - r.period_end) AS delai_depot_jours, -- LAG : les mêmes ratios, un an avant (l'évolution est un signal fort) LAG(r.marge_nette) OVER (PARTITION BY r.reg_code ORDER BY r.report_year) AS marge_nette_prev, LAG(r.liquidite) OVER (PARTITION BY r.reg_code ORDER BY r.report_year) AS liquidite_prev, LAG(r.roa) OVER (PARTITION BY r.reg_code ORDER BY r.report_year) AS roa_prev, LAG(r.dette_sur_actif)OVER (PARTITION BY r.reg_code ORDER BY r.report_year) AS levier_prev, -- benchmark secteur (pour capter le positionnement relatif) b.liquidite_p10, b.liquidite_p50, -- cible (proxy de défaut) d.en_detresse FROM marts.ratios r LEFT JOIN marts.benchmarks_emtak b ON b.emtak_section = r.emtak_section AND b.report_year = r.report_year LEFT JOIN marts.distress_label d ON d.reg_code = r.reg_code ) SELECT *, -- --- Leading indicators (détériorations) — les features qui prédisent ---- (marge_nette < marge_nette_prev) AS marge_en_baisse, (liquidite < liquidite_prev) AS liquidite_en_baisse, (roa < roa_prev) AS rentabilite_en_baisse, (dette_sur_actif > levier_prev) AS levier_en_hausse, (liquidite < liquidite_p10) AS sous_benchmark_liquidite FROM feat WHERE report_year = (SELECT MAX(report_year) FROM marts.ratios); -- dernière année connue -- 4.2 --- Annuaires de pertes consécutives (persistance de la perte) -------- -- On détecte les entreprises qui enchaînent les pertes : un signal de risque. WITH pertes AS ( SELECT reg_code, report_year, net_profit, (net_profit < 0) AS en_perte, LAG(net_profit) OVER (PARTITION BY reg_code ORDER BY report_year) AS np_prev FROM raw.annual_reports WHERE NOT COALESCE(consolidated, false) ), series AS ( SELECT reg_code, report_year, en_perte, -- on "casse" la continuité dès qu'on repasse en profit → les segments = suites de pertes SUM(CASE WHEN en_perte THEN 0 ELSE 1 END) OVER (PARTITION BY reg_code ORDER BY report_year) AS grp FROM pertes ) SELECT reg_code, COUNT(*) AS annees_consecutives_perte FROM series WHERE en_perte GROUP BY reg_code, grp ORDER BY annees_consecutives_perte DESC LIMIT 30; -- 4.3 --- Table prête à exporter vers Python (colonne "target" renommée) ---- -- Copier le résultat de 4.1 dans un CSV / dataframe = l'entrée du modèle PD. -- (colonne cible : en_detresse)
05 · Scoring Step 5

Altman-Z Score · Explainable score, in SQL

A simple but explainable credit score computed entirely in SQL and then tested against the target. The point: does the score actually separate distressed companies? The confusion-matrix query is the root of every PD model evaluation — AUC, precision, sensitivity. This is the SQL → ML bridge.

Altman-Z from balance sheetScore split vs targetConfusion matrix
-- ========================================================================= -- 05 — SCORING : un score de crédit type Altman-Z, calculé en SQL, puis validé -- Un score simple mais expliquable : on le teste contre la cible pour voir -- s'il sépare bien les entreprises en détresse. C'est le pont SQL -> ML. -- ========================================================================= -- 5.1 --- Altman-Z adapté au bilan présent -------------------------------- -- Z = 1.2*X1 + 1.4*X2 + 3.3*X3 + 0.6*X4 + 1.0*X5 -- X1 = fonds de roulement / actif ; X2 = résultats reportés / actif ; -- X3 = résultat d'exploitation / actif ; X4 = capitaux propres / dettes ; -- X5 = ventes / actif. WITH z AS ( SELECT reg_code, report_year, (current_assets - current_liabilities) AS wc, retained_earnings AS re, operating_profit AS ebit, equity AS eq, (current_liabilities + non_current_liabilities) AS dettes, revenue AS ventes, assets AS actif FROM raw.annual_reports WHERE NOT COALESCE(consolidated, false) AND assets > 0 ) SELECT reg_code, report_year, ROUND(1.2*(wc/actif) + 1.4*(re/actif) + 3.3*(ebit/actif) + 0.6*(eq/dettes) + 1.0*(ventes/actif), 2) AS z_score, CASE WHEN 1.2*(wc/actif) + 1.4*(re/actif) + 3.3*(ebit/actif) + 0.6*(eq/dettes) + 1.0*(ventes/actif) > 2.99 THEN 'green' -- sain WHEN 1.2*(wc/actif) + 1.4*(re/actif) + 3.3*(ebit/actif) + 0.6*(eq/dettes) + 1.0*(ventes/actif) >= 1.81 THEN 'grey' -- zone de vigilance ELSE 'red' -- zone de détresse END AS z_zone FROM z WHERE report_year = (SELECT MAX(report_year) FROM raw.annual_reports); -- 5.2 --- Quand le score sépare-t-il la cible ? (moyenne/median par groupe) -- -- Si le score est utile, les entreprises en détresse doivent avoir un Z-score -- nettement plus bas que les autres. WITH z AS ( SELECT a.reg_code, a.report_year, 1.2*((a.current_assets - a.current_liabilities)/a.assets) + 1.4*(a.retained_earnings/a.assets) + 3.3*(a.operating_profit/a.assets) + 0.6*(a.equity/(a.current_liabilities + a.non_current_liabilities)) + 1.0*(a.revenue/a.assets) AS z_score FROM raw.annual_reports a WHERE NOT COALESCE(a.consolidated, false) AND a.assets > 0 AND a.report_year = (SELECT MAX(report_year) FROM raw.annual_reports) ) SELECT d.en_detresse, COUNT(*) AS nb, ROUND(AVG(z.z_score), 3) AS z_moyen, ROUND(PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY z.z_score), 3) AS z_median FROM z JOIN marts.distress_label d ON d.reg_code = z.reg_code GROUP BY d.en_detresse; -- 5.3 --- Matrice de confusion du score vs cible (seuil simple) ------------ -- On convertit le score en prédiction binaire (seuil z<1.81 = "défaut") et on -- le compare à la vraie cible : on obtient TN/FP/FN/TP. C'est la racine de -- l'évaluation de tout modèle PD (AUC, précision, sensibilité). WITH z AS ( SELECT a.reg_code, 1.2*((a.current_assets - a.current_liabilities)/a.assets) + 1.4*(a.retained_earnings/a.assets) + 3.3*(a.operating_profit/a.assets) + 0.6*(a.equity/(a.current_liabilities + a.non_current_liabilities)) + 1.0*(a.revenue/a.assets) AS z_score FROM raw.annual_reports a WHERE NOT COALESCE(a.consolidated, false) AND a.assets > 0 AND a.report_year = (SELECT MAX(report_year) FROM raw.annual_reports) ) SELECT (z.z_score < 1.81) AS pred_defaut, d.en_detresse AS vrai_defaut, COUNT(*) AS nb FROM z JOIN marts.distress_label d ON d.reg_code = z.reg_code GROUP BY 1, 2 ORDER BY 1, 2; -- Interprétation : (pred=F, vrai=T) = faux négatifs → le score a raté des défauts.
06 · Window Step 6

Time Intelligence · The advanced window functions

The patterns that appear everywhere in risk analytics: a 3-year rolling mean to smooth noise, RANK / PERCENT_RANK inside a sector to see who's the most indebted of their branch, FIRST_VALUE vs LAST_VALUE to detect deterioration, and the classic run-length for 3+ consecutive loss years.

Rolling 3-year meanRANK / PERCENT_RANK by sectorFirst vs last value
-- ========================================================================= -- 06 — WINDOW / TIME INTELLIGENCE : les fenêtres avancées -- Ces motifs se retrouvent partout en analyse risque. À connaître par cœur. -- ========================================================================= -- 6.1 --- Moyenne glissante sur 3 ans de marge nette ----------------------- -- Fenêtre "ROWS BETWEEN n PRECEDING AND CURRENT ROW" : moyenne mobile, -- lisse les à-coups pour voir la tendance de fond. WITH r AS ( SELECT reg_code, report_year, revenue, net_profit, ROUND(100.0 * net_profit / NULLIF(revenue,0), 2) AS marge FROM raw.annual_reports WHERE NOT COALESCE(consolidated, false) AND revenue > 0 ) SELECT reg_code, report_year, marge, ROUND(AVG(marge) OVER (PARTITION BY reg_code ORDER BY report_year ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS marge_moy3 FROM r ORDER BY reg_code, report_year; -- 6.2 --- Rang et pourcentile de levier DANS le secteur -------------------- -- RANK / PERCENT_RANK par secteur : qui est le plus endetté de sa branche ? SELECT reg_code, emtak_section, dette_sur_actif, RANK() OVER (PARTITION BY emtak_section ORDER BY dette_sur_actif DESC) AS rang_levier, PERCENT_RANK() OVER (PARTITION BY emtak_section ORDER BY dette_sur_actif DESC) AS pct_levier FROM marts.ratios WHERE report_year = (SELECT MAX(report_year) FROM marts.ratios) ORDER BY emtak_section, rang_levier; -- 6.3 --- Détérioration : dernier rapport vs premier rapport ---------------- -- FIRST_VALUE vs LAST_VALUE : mesure si l'entreprise s'est dégradée depuis -- son premier rapport disponible. WITH r AS ( SELECT reg_code, report_year, roa, solvabilite, liquidite FROM marts.ratios ) SELECT reg_code, report_year, FIRST_VALUE(roa) OVER (PARTITION BY reg_code ORDER BY report_year) AS roa_1er, LAST_VALUE(roa) OVER (PARTITION BY reg_code ORDER BY report_year ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS roa_dernier, (LAST_VALUE(roa) OVER (PARTITION BY reg_code ORDER BY report_year ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) - FIRST_VALUE(roa) OVER (PARTITION BY reg_code ORDER BY report_year)) AS delta_roa FROM r WHERE report_year = (SELECT MAX(report_year) FROM marts.ratios) ORDER BY delta_roa; -- 6.4 --- Entreprises avec 3+ années consécutives de résultat négatif ------ -- Le classique "run" : on détecte les longues séquences de pertes. WITH pertes AS ( SELECT reg_code, report_year, (net_profit < 0) AS en_perte FROM raw.annual_reports WHERE NOT COALESCE(consolidated, false) ), series AS ( SELECT reg_code, report_year, en_perte, SUM(CASE WHEN en_perte THEN 0 ELSE 1 END) OVER (PARTITION BY reg_code ORDER BY report_year) AS grp FROM pertes ) SELECT reg_code, COUNT(*) AS annees_consecutives_perte FROM series WHERE en_perte GROUP BY reg_code, grp HAVING COUNT(*) >= 3 ORDER BY annees_consecutives_perte DESC;

Methodology &
Limits

The problem

Anticipate payment default on 375,000+ Estonian companies. Target = distress proxy, not bankruptcy — the latter is a 0.18% event, rare and already too late.

The method

Six SQL passes, each a credit-analyst reflex: profile the data, rebuild ratios, benchmark vs sector, read risk in cohorts, engineer PD features, score & validate. Window functions and LAG model deterioration — the leading indicators of default.

What the proxy teaches

AUC, not accuracy. A model that predicted "nobody defaults" would be 99.8% accurate and useless.

Honest limitations

  • Target is point-in-time (Aug 2026 snapshot) — no fine-grained default history.
  • Tax arrears is a single snapshot — the real time axis is the annual reports.
  • Default is rare — so I evaluate with AUC, never accuracy.
  • TimesFM forecast is a prototype — a forward-looking extra layer, not the model.

SQL Skills Demonstrated

CTEs Window Functions LAG / LEAD FILTER (WHERE) PERCENTILE_CONT Gaps & Islands NULLIF guards

PostgreSQL on Neon. Python (pandas, XGBoost, SHAP) for the PD model. TimesFM-3 for the forward-looking layer.
